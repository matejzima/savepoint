# Savepoint - Phase 3 Build Summary

Built against [phase-3-plan.md](phase-3-plan.md) (approved as amended: window as encouraged default, worker-pool/queue window mechanism).

## What was built

- **Schema**: `targets` gained `schedule_cron` (nullable) and `in_window` (boolean); `backup_runs` gained `triggered_by` (`manual`/`schedule`/`window`); a new `settings` key-value table. All migrated in place via the same guarded `ALTER TABLE ADD COLUMN` pattern from Phase 2. `db.get_connection()` now also sets `PRAGMA journal_mode = WAL` and `PRAGMA busy_timeout = 5000`, needed once concurrent writers became real this phase.
- **`app/jobs.py`**: `try_claim()`/`release()` (a module-level lock + set of in-progress target IDs), `run_backup(target_id, triggered_by, run_id=None)` for schedule/window triggers, `execute_claimed(target_id, run_id)` for manual (see deviation below), and a private `_execute()` that is the sole caller of `ADAPTERS[engine].backup(...)`.
- **`app/scheduler.py`**: `BackgroundScheduler` setup/shutdown, `sync_target_schedule()` (adds/updates/removes a target's cron job live, no restart needed), `window_tick()` implementing the bounded worker-pool/queue design from the amended plan: every window member gets a `queued` row up front, `concurrency` worker threads pull `(target_id, run_id)` pairs via `queue.Queue.get_nowait()` (per your implementation note, not a blocking `get()`) until the queue empties or the deadline passes, then any rows still `queued` are swept to `skipped` with a "window closed" message before `notify_window_summary()` fires.
- **`app/notifications.py`**: `notify_failure()` and `notify_window_summary()`, both no-ops when `NTFY_URL`/`NTFY_TOPIC` aren't set, ntfy failures are caught and logged rather than breaking a backup job.
- **Manual run dispatch**: `POST /targets/{id}/run` now does a synchronous `try_claim()`, creates the `running` row itself if claimed, and hands off just the adapter call to APScheduler (`scheduler.dispatch_manual()`) instead of blocking the request. A collision renders an inline "already running" notice with no new row; a schedule/window collision instead produces a visible `skipped` row (fresh for schedule, updating the pre-created row for window).
- **Scheduling UI**: target detail page gained a "Schedule" section, window membership pre-selected/default, cron reframed as an explicit override with the exact warning text specified, both fields always visible (no show/hide JS, consistent with the Phase 2 add-target form precedent) with a static warning caption rather than a dynamically toggled one (see deviation below). `POST /targets/{id}/schedule` validates cron via `CronTrigger.from_crontab()`.
- **`GET/POST /settings`**: window start/duration/concurrency, with validation, plus a read-only list of current window members. Saving reloads the window's APScheduler job immediately.
- **`GET /targets/{id}/history`**: new polling endpoint; `partials/history_row.html` conditionally includes `hx-trigger="every 2s"` only while a row is `queued` or `running`, and stops polling on its own once everything is terminal (no JS beyond what HTMX already provides).
- **`requirements.txt`**: `apscheduler==3.11.3` pinned (matching the fastapi/starlette pinning convention), `requests>=2.31` added as an explicit direct dependency (see deviation below).
- Tests: `tests/test_jobs.py` (claim/release, schedule vs. window vs. manual collision handling, success/failure recording, failure triggers `notify_failure`), `tests/test_scheduler.py` (cron parsing, `sync_target_schedule` add/update/remove, the worker pool actually capping concurrency at 2 while still processing all 5 queued targets, the duration cutoff leaving unclaimed targets cleanly `skipped`, no summary sent for an empty window), `tests/test_notifications.py` (ntfy on/off, message content, exceptions swallowed).

## Deviations from the plan, and why

- **Manual dispatch is split across two functions, not one.** The plan named `run_backup(target_id, triggered_by)` as the single function used by every trigger source, including manual, dispatched via `scheduler.add_job(run_backup, args=[...])` with the route "returning right away." But the plan also requires the *route itself* to know synchronously whether the target is already busy (to render the inline notice with no new row, vs. dispatching), and that knowledge can't come from inside a job that hasn't run yet on a background thread. Resolved by having the route call `jobs.try_claim()` synchronously and create the row itself, then dispatch only `jobs.execute_claimed(target_id, run_id)` (adapter call + finish + release) to the scheduler. Both `run_backup()` (schedule/window) and `execute_claimed()` (manual) route through the same private `_execute()`, which is still the one and only place that ever calls `adapter.backup(...)`, preserving the actual intent behind the plan's invariant.
- **Schedule form warning is a static caption, not a dynamically shown/hidden element.** The plan text describes a warning that appears "when cron is chosen," which implies some interactivity. Rather than adding inline JS to toggle it, both the cron input and its warning caption are always visible (mirroring the Phase 2 add-target form's "always show all fields, server-side validation is authoritative, no show/hide JS" precedent). The warning reads as a permanent note next to the cron option rather than an animation reacting to the radio selection. Flagging this since it's a literal, if minor, gap against the plan's wording, easy to add a small toggle script later if the static version reads as unclear in practice.
- **`requests` added as an explicit dependency.** The plan said no new package was needed since `requests` already arrives transitively via `docker`. Since `notifications.py` imports it directly, pinning it explicitly (`requests>=2.31`) is more robust than depending on another package's transitive resolution staying compatible across future `docker` package upgrades.
- **`window_tick()` takes an optional `deadline` parameter.** Not in the plan; added purely so the duration-cutoff behavior could be tested deterministically (a fixed, short deadline) instead of waiting on real wall-clock minutes. Production callers never pass it, it's computed from the `window_duration_minutes` setting as the plan describes.

## Testing performed

- `pytest tests/` - 37/37 pass (previously 20 from Phases 1-2, plus 6 new `test_jobs.py`, 5 new `test_scheduler.py`, 6 new `test_notifications.py`). Reran `test_scheduler.py` five times in a row to check for timing flakiness in the concurrency-cap and duration-cutoff tests, all passed consistently.
- Booted the app against a hand-built Phase-2-shaped state db (no `schedule_cron`/`in_window`/`triggered_by`/`settings`) and confirmed all four migrate in cleanly, the pre-existing target/history row is untouched, and `/`, `/settings`, `/targets/1`, `/targets/1/history` all render.
- Full route-level flow with `TestClient` used as a context manager (so the FastAPI lifespan actually starts the scheduler, unlike a bare `TestClient(app)`) and Docker mocked:
  - Created a target, saved a cron schedule, confirmed the detail page reflects it, confirmed an invalid cron is rejected with a clear error.
  - Switched the same target to window membership, confirmed it appears on `/settings`'s member list.
  - Triggered a manual run, confirmed the request returns immediately and the target's history transitions to `success` shortly after via polling, proving the adapter call actually happened on a background thread rather than blocking the request.
  - Manually claimed a target via `jobs.try_claim()` then hit "run now", confirmed the inline "already running" notice with no duplicate row.
  - Saved window settings (start/duration/concurrency), confirmed they persist and redisplay, confirmed an invalid time format is rejected.

## Not tested here (needs the real homelab Docker host)

No Docker daemon or real multi-hour window was exercised end to end in this dev environment. Before considering Phase 3 done, run the plan's verification steps against real containers, in particular:
1. A real per-target cron schedule firing unattended (not just a mocked/instant dispatch) and showing up with `triggered_by = "schedule"`.
2. A real window run against several real containers with a genuinely tight duration, confirming leftover targets are marked `skipped` and the summary notification's skipped count matches, exactly as the amendment intended.
3. Real ntfy delivery against an actual ntfy server/topic (only the HTTP call shape was verified here, via mocked `requests.post`), confirming messages actually arrive and read clearly.
4. Watching the detail page live in a browser through a queued -> running -> success transition to confirm the polling UX feels right and stops promptly, not just that the server-rendered HTML omits the `hx-trigger` attribute once terminal.
